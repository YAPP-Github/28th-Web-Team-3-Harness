# Main 구현 기준 Harness 역문서화 설계

## 목표

개발이 완료된 FE와 BE의 최신 `main` 구현을 근거로 홈·온보딩·미션·혜택·마이페이지의 공통 도메인 정책과 사용자 플로우를 Harness에 역문서화한다. 이후 개선·수정·운영 작업은 이 문서를 읽고 시작할 수 있어야 한다.

## 고정 기준

- Harness: `YAPP-Github/28th-Web-Team-3-Harness` `main` 커밋 `d6c9f2da757b9688a6748d0e766354737904a3ff`
- FE: `YAPP-Github/28th-Web-Team-3-FE` `main` 커밋 `6ba701fb3c85a8980ab090b9321f645edcfab325`
- BE: `YAPP-Github/28th-Web-Team-3-BE` `main` 커밋 `6deb8af2f5e167cbbaf0d15ce9a025cf7c7a6227`
- 작업 도중 원격 `main`이 바뀌어도 모듈 간 기준이 달라지지 않도록 위 커밋을 끝까지 사용한다.

## 정책 판정 원칙

- FE는 사용자가 보는 화면, 입력, 전환, 안내와 오류 복구 동작의 근거로 사용한다.
- BE는 저장 데이터, 유효성 규칙, 상태 전이, 권한과 불변조건의 근거로 사용한다.
- 양쪽이 같은 동작을 표현하면 공통 정책으로 확정한다.
- 한쪽에만 존재하는 구현은 다른 쪽과 모순되지 않을 때만 적용 범위를 밝혀 기록한다.
- FE와 BE가 충돌하거나 의미를 확정할 근거가 부족하면 추론하지 않는다. 문서의 예외 또는 결정 기록에 차이와 확인 필요 사항을 남긴다.
- 컴포넌트, 프레임워크, 캐시 라이브러리, DB 구현 같은 기술 세부사항은 공통 정책으로 기록하지 않는다.
- 실제 시크릿, 인증 정보, 개인정보와 환경별 실제 URL은 기록하지 않는다.

## 독립 브랜치

모든 브랜치는 Harness 기준 커밋에서 직접 분기하며 서로를 기반으로 삼지 않는다.

| 브랜치 | 모듈 | 주요 범위 |
| --- | --- | --- |
| `codex/harness-home` | 홈 | 목표 진행 현황, 이번 주 미션 요약, 절약 팁 |
| `codex/harness-onboarding` | 온보딩 | 게스트 진입, 질문 입력·검증, 확인, 목표, 결과 |
| `codex/harness-mission` | 미션 | 설문, AI·직접 생성, 확정, 수행, 완료·삭제, 기록 |
| `codex/harness-benefits` | 혜택 | 정책·절약 팁, 필터, 저장, 저장 목록, 외부 상세 이동 |
| `codex/harness-mypage` | 마이페이지 | 약관, 개인정보처리방침, 문의, 앱 버전, 탈퇴 |

## 모듈별 산출물

각 브랜치는 독립적으로 다음 조건을 만족한다.

- 필요한 정책 문서를 `domain/policies/`에 작성하거나 기존 문서를 최신 구현에 맞게 수정한다.
- 정상 흐름과 실패·복구 흐름을 `domain/workflows/`에 작성하거나 수정한다.
- FE·BE 기준 커밋, 조사 범위, 구현 불일치를 `decisions/2026-08-25-<module>-main-baseline.md`에 기록한다.
- 새 공통 용어를 `domain/glossary.md`에 등록한다.
- 정책과 플로우만으로 놓치기 쉬운 경합·복구·데이터 특이사항이 있으면 `domain/exceptions.md`에 추가한다.
- 기존 API 필드 의미 문서가 현재 구현과 충돌할 때만 `domain/api-field-mappings/`를 수정한다.
- 정책·플로우·결정 ID를 상대 링크로 연결한다.

## 기존 문서 처리

- 미션 브랜치는 기존 정책·플로우·결정 기록을 우선 대조하고 수정한다. 같은 의미의 새 문서를 중복 생성하지 않는다.
- 온보딩 브랜치는 기존 API 필드 매핑을 근거로 사용할 수 있지만, 정책·플로우는 별도로 완성한다.
- 혜택·마이페이지의 기존 미병합 브랜치 `codex/docs-mypage-benefits`는 참고 자료일 뿐 기준이 아니다. 최신 FE·BE `main`에서 다시 검증하고 모듈별 새 브랜치에 분리한다.
- 홈은 혜택과 미션의 요약 정보를 보여 주더라도 홈에서 발생하는 조회·표시·이동만 다룬다. 세부 생성·저장 규칙은 해당 모듈 문서에 맡긴다.

## 병렬 작업과 충돌 경계

- 각 작업자는 자신의 worktree와 모듈 브랜치만 수정한다.
- 공통 파일인 `domain/glossary.md`와 `domain/exceptions.md`는 자기 모듈에 필요한 최소 행·항목만 추가한다.
- 다른 브랜치의 커밋을 병합하거나 cherry-pick하지 않는다.
- 모듈 브랜치는 각각 독립 검증과 리뷰를 통과한 상태로 푸시한다. 병합 시 공통 파일 충돌 해결은 후속 PR 작업 범위다.

## 검증 기준

각 브랜치에서 다음을 확인한다.

- Harness 구조와 `.claude` 심볼릭 링크
- 정책·플로우 ID 중복과 파일명 규칙
- 템플릿 필수 섹션
- 정책·플로우·결정의 상대 링크
- 새 용어의 정의와 정책 링크
- 시크릿·인증 정보·개인정보 부재
- FE·BE 고정 기준 커밋과 문서 내용의 일치
- 모듈 범위 밖 기술 규칙과 추론된 정책 부재

## 완료 상태

- 모듈별 AI 검토에서 중요 이상 지적을 해결한다.
- 각 브랜치 작업 트리가 깨끗하다.
- 각 브랜치 변경을 의미 단위 커밋으로 기록한다.
- `origin`에 같은 이름으로 푸시한다.
- GitHub PR은 생성하지 않는다.
